# Confd Dynamic Plugin Architecture Demo

This guide will walk you through testing the entirely new **HashiCorp `go-plugin`** architecture of `confd`. 
Instead of using a statically compiled backend, we will use a standalone compiled binary (`confd-plugin-postgres`) that `confd` will communicate with dynamically over RPC!

---

## 1. Preparation & Compilation

First, make sure both the main `confd` binary and our external Postgres plugin are compiled up to date.

```bash
# 1. Vendor dependencies
go mod vendor

# 2. Compile the core confd binary
make build

# 3. Compile the standalone Postgres Plugin
go build -o bin/confd-plugin-postgres ./cmd/confd-plugin-postgres
```

---

## 2. Start PostgreSQL

We will use the same Docker environment as before. Start it up:

```bash
docker compose -f test/docker-compose.yml up -d postgres
```

Wait a few seconds for the database to boot, then run the setup script that creates the table, triggers (validation + audit + NOTIFY), and seeds the initial data:

```bash
docker compose -f test/docker-compose.yml exec -T postgres \
  psql -U admin -d confd < test/integration/backends/postgres/setup.sql
```

---

## 3. Create the Confd Workspace

We will create a fresh workspace in `/tmp/confd-plugin-demo`.

```bash
mkdir -p /tmp/confd-plugin-demo/conf.d
mkdir -p /tmp/confd-plugin-demo/templates
mkdir -p /tmp/confd-plugin-demo/output

# Create the resource file
cat << 'EOF' > /tmp/confd-plugin-demo/conf.d/app.toml
[template]
src = "app.conf.tmpl"
dest = "/tmp/confd-plugin-demo/output/app.conf"
keys = [ "/app" ]
check_cmd = "grep -q 'Syntax:OK' {{.src}}"
reload_cmd = "echo '====> [PLUGIN RELOADED] Config updated via RPC! <===='"
EOF

# Create the template
cat << 'EOF' > /tmp/confd-plugin-demo/templates/app.conf.tmpl
# Generated by external confd plugin!
# Timestamp: {{datetime}}

{{if eq (getv "/app/feature_flags/maintenance") "true"}}
Syntax:INVALID (System is in maintenance)
{{else}}
Syntax:OK
{{end}}

[database]
endpoint = {{getv "/app/database/host"}}:{{getv "/app/database/port"}}
EOF
```

## 4. Test 1: One-Time Run via Plugin

Now, the moment of truth! We will launch `confd` using the `plugin` subcommand and provide it the path to our freshly compiled binary.

### How does the plugin get configured?

The `confd-plugin-postgres` binary is a **real CLI tool** with its own flags. You can see them with:
```bash
./bin/confd-plugin-postgres --help
```
```text
Usage of ./bin/confd-plugin-postgres:
  -database string
        Postgres database name (default "confd")
  -node string
        Postgres node endpoint (default "127.0.0.1:5432")
  -password string
        Postgres password (default "secret")
  -table string
        Postgres table name (default "confd_config")
  -username string
        Postgres username (default "admin")
```

When `confd` spawns the plugin as a subprocess, the plugin **inherits the parent's environment variables**. If an environment variable is set, it overrides the default CLI flag value. This means you can configure it either way:

| Plugin CLI Flag | Environment Variable | Default |
| :--- | :--- | :--- |
| `--node` | `CONFD_BACKEND_NODE` | `127.0.0.1:5432` |
| `--username` | `CONFD_USERNAME` | `admin` |
| `--password` | `CONFD_PASSWORD` | `secret` |
| `--database` | `CONFD_DATABASE` | `confd` |
| `--table` | `CONFD_TABLE` | `confd_config` |

### Run it!

```bash
# Set the environment variables (inherited by the plugin subprocess)
export CONFD_BACKEND_NODE="127.0.0.1:5432"
export CONFD_USERNAME="admin"
export CONFD_PASSWORD="secret"
export CONFD_DATABASE="confd"
export CONFD_TABLE="confd_config"

# Launch confd with the plugin backend
./bin/confd plugin \
  --plugin-path "./bin/confd-plugin-postgres" \
  --confdir /tmp/confd-plugin-demo \
  --onetime
```

If it works, `confd` will start the plugin subprocess, perform RPC calls to fetch the values, and generate the config file!

Verify the output:
```bash
cat /tmp/confd-plugin-demo/output/app.conf
```

## 5. Test 2: Real-Time LISTEN/NOTIFY Mode (Event-Driven)

This is the **star feature**. Instead of polling the database every N seconds, `confd` now uses PostgreSQL's native `LISTEN/NOTIFY` mechanism. The database **pushes** events to `confd` the instant a change occurs.

### How it works

```
Traditional Polling:   confd → every 3s → "anything new?" → DB responds
LISTEN/NOTIFY:         confd → LISTEN → sleeps... → DB: NOTIFY! → confd wakes up INSTANTLY
```

The `setup.sql` script we ran earlier created a `trigger_notify` function that calls `pg_notify('confd_update', ...)` on every INSERT/UPDATE. Our Go code subscribes to that channel with `LISTEN confd_update` and blocks until a notification arrives.

### Launch confd in watch mode

```bash
./bin/confd plugin \
  --plugin-path "./bin/confd-plugin-postgres" \
  --confdir /tmp/confd-plugin-demo \
  --watch &

CONFD_PID=$!
```

**👀 Expected Visual Output (in your terminal):**
You will see confd start the plugin and subscribe to the notification channel:
```text
INFO  Starting confd
INFO  Backend set to plugin
INFO  Backend source(s) set to Plugin ./bin/confd-plugin-postgres
[postgres] LISTEN/NOTIFY: waiting for events on channel 'confd_update'...
```

### Trigger a real-time update (in another terminal)

```bash
docker compose -f test/docker-compose.yml exec -T postgres psql -U admin -d confd -c "
UPDATE confd_config SET value = '6432' WHERE key = '/app/database/port';
"
```

**👀 Expected Visual Output (back in the first terminal):**
The update is detected **instantly** (no 3-second delay). You will see:
```text
[postgres] NOTIFY received: channel=confd_update payload=/app/database/port=6432
INFO  Target config /tmp/confd-plugin-demo/output/app.conf out of sync
INFO  Command completed successfully command=grep -q 'Syntax:OK' ...
INFO  File sync completed (atomic rename)
INFO  Command completed successfully command=echo '====> [PLUGIN RELOADED] ...'
INFO  Target config /tmp/confd-plugin-demo/output/app.conf has been updated
[postgres] LISTEN/NOTIFY: waiting for events on channel 'confd_update'...
```

> **Note:** The `reload_cmd` output is captured by confd and logged as an INFO line.
> After the update, confd immediately re-subscribes to wait for the next event.

## 6. Test 3: Polling Fallback Mode

If for some reason LISTEN/NOTIFY is not available (e.g., a proxy blocks persistent connections), `confd` falls back gracefully to the classic polling mode using `--interval`:

```bash
# Kill the previous watch-mode confd
pkill confd

# Restart in polling mode (checks every 3 seconds)
./bin/confd plugin \
  --plugin-path "./bin/confd-plugin-postgres" \
  --confdir /tmp/confd-plugin-demo \
  --interval 3 &

CONFD_PID=$!
```

Update the database again:
```bash
docker compose -f test/docker-compose.yml exec -T postgres psql -U admin -d confd -c "
UPDATE confd_config SET value = '5433' WHERE key = '/app/database/port';
"
```

**👀 Expected Visual Output:**
Within 3 seconds (the polling interval), the reload message appears:
```text
====> [PLUGIN RELOADED] Config updated via RPC! <====
```

## 7. Test 4: The "Bouncer" (Security & Validation)

Let's try to inject a completely invalid port number (`99999`) into our database. Normally, a dumb system would crash the app. But thanks to our PostgreSQL Trigger, the database acts as a bouncer!

```bash
docker compose -f test/docker-compose.yml exec -T postgres psql -U admin -d confd -c "
UPDATE confd_config SET value = '99999' WHERE key = '/app/database/port';
"
```

**👀 Expected Visual Output:**
The database will instantly violently reject the SQL command!
```text
ERROR:  Invalid port number: 99999
CONTEXT:  PL/pgSQL function validate_config() line 5 at RAISE
```
Because the DB rejected it, the plugin never sends the bad data to `confd`, and your system stays 100% safe!

## 8. Test 5: Graceful Syntax Rejection (Maintenance Mode)

Now, let's trigger the "Maintenance Mode". This time, the DB will accept the change, but our `confd` template will intentionally generate a bad syntax file (`Syntax:INVALID`). 
`confd`'s `check_cmd` will catch it!

```bash
docker compose -f test/docker-compose.yml exec -T postgres psql -U admin -d confd -c "
UPDATE confd_config SET value = 'true' WHERE key = '/app/feature_flags/maintenance';
"
```

**👀 Expected Visual Output:**
Because the syntax check fails, `confd` will refuse to apply the file and will throw an error to protect your production server:
```text
ERROR config check failed: exit status 1
```

To fix it and return to normal:
```bash
docker compose -f test/docker-compose.yml exec -T postgres psql -U admin -d confd -c "
UPDATE confd_config SET value = 'false' WHERE key = '/app/feature_flags/maintenance';
"
```
```text
====> [PLUGIN RELOADED] Config updated via RPC! <====
```

## 9. Test 6: Exploring the Audit Trail

Everything you just did via the plugin was permanently recorded by the `trigger_audit` inside the database. Let's look at the history!

```bash
docker compose -f test/docker-compose.yml exec -T postgres psql -U admin -d confd -c "
SELECT action, key, old_value, new_value, changed_at FROM config_audit ORDER BY changed_at DESC LIMIT 5;
"
```

**👀 Expected Visual Output:**
A beautiful table showing every state transition you performed during this demo!
